# Guardium TechZone Bootcamp Automation

Python automation framework for deploying and configuring IBM Guardium bootcamp environments on IBM TechZone VPC Multi-VM.

The framework runs as a TechZone **post-deploy script** on the `raptor` control node and provisions all VMs (raptor, sauropod, ceratops) from scratch — databases, Guardium appliances, agents, and lab content — in a single automated run.

## 🚀 Quick Start

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Run automation (deployment_type is read from machines_info.json)
python automation.py

# 3. Check what was executed
python automation.py --status
```

The script reads `/root/machines_info.json` (auto-generated by TechZone post-deploy) to obtain machine IPs and custom variables.

---

## ⚙️ machines_info.json

This file is written by the TechZone post-deploy playbook and consumed automatically:

```json
{
  "machines": [
    { "name": "raptor-xyz",   "public_ip": "...", "private_ip": "..." },
    { "name": "sauropod-xyz", "public_ip": "...", "private_ip": "..." },
    { "name": "ceratops-xyz", "public_ip": "...", "private_ip": "..." }
  ],
  "custom_variables": {
    "pwd":             "Guardium1!",
    "deployment_type": "standard_demo",
    "cli_pwd":         "...",
    "cloudsupport_pwd":"...",
    "shared_secret":   "guardium"
  }
}
```

### `deployment_type` values

| Value             | Groups executed automatically                          |
|-------------------|--------------------------------------------------------|
| `init`            | `initial_preparation` only                             |
| `databases`       | `initial_preparation` → `database_preparations`        |
| `appliances`      | above + `setup_appliances` → `gim_lab` → `atap_lab` → `exit_lab` → `etap_lab` |
| `standard_demo`   | above + `va_basics` → `winstap_lab` → `oracle_lab` → `policies_reports_part1` → `va_api` |
| `new_architecture`| above + `ltr_lab` → `edge_lab`                        |

Groups not listed in a deployment type (e.g. `oracle_lab_uc2`, `fam_lab`, `uc1_lab`) have `deployed_with: []` and must be run manually with `--group`.

## 🎯 CLI Options

```
python automation.py [OPTIONS]
```

| Option | Description |
|--------|-------------|
| *(no options)* | Run groups for the `deployment_type` defined in `machines_info.json` |
| `--group GROUP` | Run a specific group (can be repeated for multiple groups) |
| `--stage STAGE` | Run a single stage by name (plus all preceding stages in the same group) |
| `--continue` | Execute all remaining stages across all groups (resumes after failure) |
| `--status` | Print per-group / per-stage completion status |
| `--list-groups` | Print all groups and their stages |
| `--reset` | Clear `state.json` — all stages will re-execute |
| `--remove-stage GROUP.STAGE` | Mark a single stage as not-completed so it re-runs |
| `--config FILE` | Override config file path (default: `config/config.yaml`) |
| `--groups-config FILE` | Override groups file path (default: `config/groups.yaml`) |
| `--machines-info FILE` | Override machines_info path (default: `/root/machines_info.json`) |
| `--state FILE` | Override state file path (default: `state.json`) |
| `--verbose` / `-v` | Enable verbose output |
| `--skip-deps` | Skip dependency checks when running `--group` *(use with caution)* |

### Examples

```bash
# Run only the GIM lab (resolves dependencies automatically)
python automation.py --group gim_lab

# Run LTR and Edge labs back-to-back
python automation.py --group ltr_lab --group edge_lab

# Re-run a single stage that failed
python automation.py --remove-stage ltr_lab.activate_ltr
python automation.py --group ltr_lab

# Resume after a crash
python automation.py --continue

# Check progress
python automation.py --status
```

## 📋 Groups Overview

Groups execute in dependency order. Each group is made up of sequential **stages**.

| Group | Display name | Key content |
|-------|--------------|-------------|
| `initial_preparation` | Initial Preparation | /etc/hosts, packages, uploads, swap, ceratops setup (Edge browser, MSSQL, FAM files, RDP relay) |
| `database_preparations` | Standard Databases | MySQL 9, MongoDB 8, PostgreSQL 16, Oracle 21c container, Db2 11.5, Cassandra 4.1, Informix 15 |
| `setup_appliances` | Setup Appliances | CLI password reset, OAuth client, demo user, system settings, shared secret, patches, policy install |
| `gim_lab` | GIM Lab | Import GIM modules to CM |
| `atap_lab` | ATAP Lab | Install GIM+STAP on raptor, ATAP for PostgreSQL/MongoDB, IE fix, verification definitions |
| `exit_lab` | Exit Lab | Db2 Exit configuration and Inspection Engine |
| `uc1_lab` | UC 1.0 Lab | Filebeat on sauropod for Cassandra UC 1.0 |
| `etap_lab` | ETAP Lab | Packages, ETAP certificates, deploy mysql-etap container |
| `va_basics` | VA Basics Lab | Enable VA feature, VA account, DPS import, VA Scanner on sauropod |
| `winstap_lab` | WinSTAP Lab | GIM + WinSTAP install on ceratops |
| `fam_lab` | FAM Lab | FAM configure on raptor, FAM policy, FAMMONITOR on ceratops |
| `oracle_lab` | Oracle Lab | STAP on sauropod, ATAP for Oracle, ETAP for Oracle, OUA, audit policy, Oracle dashboard |
| `oracle_lab_uc2` | Oracle Lab UC2 | Run UC, Kafka node setup, register cluster, import UC profile, cycle Kafka, test connection, bulk install |
| `policies_reports_part1` | Policies and Reports | App profile, engine config, firewall flags, dbtraffic run, app data access policy, dashboard |
| `va_api` | VA API | VA dashboard + Oracle assessment definitions, VA OAuth client |
| `ltr_lab` | LTR Lab | MinIO setup, appnode configuration, datalake patch, LTR enable, cert import/distribute, activate LTR, LTR dashboard |
| `edge_lab` | Edge Lab | Edge patch on CM, k3s on sauropod, Edge Gateway register/deploy/monitor, STAP for Edge on ceratops |

## 🔄 State Management

The framework tracks completed stages in `state.json` (format: `group_name.stage_name`).

- A stage that is already completed is **skipped** on the next run (shown as `⏭`).
- On success the stage is marked `✓`, on failure `✗` — and the group stops.
- Use `--remove-stage` to force re-execution of a single stage.
- Use `--reset` to start completely from scratch.

## 📝 Adding a New Stage / Group

**1. Create a function in `tasks/my_module.py`:**

```python
def my_stage(config, logger, verbose: bool = False, **kwargs) -> bool:
    _header(logger, "My Stage Title")
    # ... implementation ...
    return True
```

> All stage functions **must** accept `**kwargs` — the orchestrator passes stage `args:` from `groups.yaml` as keyword arguments.

**2. Register in `config/groups.yaml`:**

```yaml
groups:
  my_group:
    name: "My Group"
    description: "What this group does"
    deployed_with: [standard_demo]   # or [] for manual-only
    dependencies: [setup_appliances]
    stages:
      - name: my_stage
        function: my_stage
        module: tasks.my_module
        description: "What this stage does"
        args:
          debug: false
```

**3. Run:**

```bash
python automation.py --group my_group
```

## 🐛 Troubleshooting

**SSH connection fails:**
```bash
ssh root@<machine_ip> -p 2223
```

**Stage failed, want to retry:**
```bash
python automation.py --remove-stage group_name.stage_name
python automation.py --group group_name
```

**Check detailed logs:**
```bash
tail -200 logs/automation_*.log
```

**Start completely fresh:**
```bash
python automation.py --reset
python automation.py
```

**State file corrupted:**
```bash
rm state.json
python automation.py
```
